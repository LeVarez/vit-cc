  <action>
  Create `.claude/agents/vit-pr-reviewer.md` with the following structure:

  **Frontmatter:**
  ```yaml
  ---
  name: vit-pr-reviewer
  description: Reviews promoted PRs and posts severity-tiered findings as GitHub review comments. Spawned by verify-work after PR promotion (Route A).
  tools: Bash, Read
  color: purple
  ---
  ```

  **Role section:**
  State that this agent reviews PRs by reading the diff, analyzing code changes, and posting structured findings back to GitHub. It is spawned by verify-work and receives PR_NUM, REPO, and WORK_DIR in its prompt context.

  **Execution flow with these steps:**

  **Step 1: Parse context from prompt.**
  Extract from the prompt context provided by verify-work:
  - `PR_NUM` — the PR number to review
  - `REPO` — the repo slug (owner/name)
  - `WORK_DIR` — absolute path to the working directory
  - `PHASE_NUM` — phase number
  - `PHASE_NAME` — phase name

  **Step 2: Fetch PR diff and HEAD SHA.**
  ```bash
  cd "$WORK_DIR" && DIFF=$(gh pr diff $PR_NUM 2>/dev/null)
  cd "$WORK_DIR" && HEAD_SHA=$(gh pr view $PR_NUM --json headRefOid --jq '.headRefOid' 2>/dev/null)
  ```
  If either fails, log `[reviewer: failed to fetch PR data — skipping review]` and exit gracefully.

  **Step 3: Analyze the diff.**
  The agent (Claude) reads the raw diff and produces a structured review. The agent prompt must include these instructions for self-analysis:

  > Analyze this PR diff for code quality issues. Categorize each finding into one of three severity tiers:
  >
  > - **block-merge**: Issues that should be resolved before merging (bugs, security issues, data loss risks, broken functionality)
  > - **should-fix**: Issues worth fixing in this PR but not merge-blocking (code smells, missing error handling, performance concerns)
  > - **nit**: Minor suggestions (style, naming, minor simplifications)
  >
  > For each finding, provide:
  > 1. The file path (exactly as shown in the diff after `+++ b/`)
  > 2. The line number (must be a line that starts with `+` in the diff — an addition, NOT a deletion)
  > 3. The severity tier
  > 4. A brief explanation (1-2 sentences)
  >
  > IMPORTANT: Only reference lines that begin with `+` (additions) in the diff. Never reference deleted lines (starting with `-`). If the diff is clean and you find no meaningful issues, say so — do not invent findings.
  >
  > Select up to 5 findings for inline comments, prioritized by severity (block-merge first, then should-fix, then nit). All findings go in the body summary regardless of count.

  Since the agent IS Claude, the "analysis" is simply reading the diff content and producing the structured output. No separate LLM call is needed — the agent itself performs the review.

  **Step 4: Post body summary comment.**
  Format the review body using this template:
  ```markdown
  ## AI Review — Phase {PHASE_NUM}: {PHASE_NAME}

  > Auto-generated by `vit-pr-reviewer`. Does not approve or block merge.

  ### block-merge
  {findings or "None"}

  ### should-fix
  {findings or "None"}

  ### nit
  {findings or "None"}

  ---
  _Inline comments posted on up to 5 highest-severity findings above._
  ```

  Post via:
  ```bash
  cd "$WORK_DIR" && gh pr review $PR_NUM --comment --body "$REVIEW_BODY" 2>/dev/null || true
  ```

  CRITICAL: Use `--comment` only. NEVER use `--approve` or `--request-changes`. This avoids HTTP 422 errors (PRR-04 / success criterion 4).

  **Step 5: Post inline diff comments (up to 5).**
  Take the top 5 findings (by severity: block-merge > should-fix > nit) and build a JSON comments array:

  ```json
  [
    {
      "path": "src/example.ts",
      "line": 42,
      "side": "RIGHT",
      "body": "[block-merge] Unhandled promise rejection — fetchUser() can throw but caller has no try/catch"
    }
  ]
  ```

  Rules for inline comments:
  - `path`: Must match the file path from the diff (after `+++ b/`)
  - `line`: Must be a line number that appears as a `+` (addition) or ` ` (context) line in the diff. NEVER use deleted lines.
  - `side`: Always `"RIGHT"` (new file side). Do NOT use `"LEFT"`.
  - `body`: Prefix with `[severity]` tag. Keep to 1-2 sentences.
  - Maximum 5 comments. If fewer than 5 findings exist, post only the ones found.
  - If zero findings, skip this step entirely.

  Post via:
  ```bash
  cd "$WORK_DIR" && gh api "repos/$REPO/pulls/$PR_NUM/reviews" \
    --method POST \
    -H "Accept: application/vnd.github+json" \
    --input - <<EOF
  {
    "commit_id": "$HEAD_SHA",
    "event": "COMMENT",
    "body": "",
    "comments": $COMMENTS_JSON
  }
  EOF
  ```

  If the `gh api` call fails (422 or other error), log `[reviewer: inline comments failed — body summary was posted successfully]` and continue. Do NOT abort. The body summary is the primary output; inline comments are best-effort.

  **Fallback note:** If `body: ""` causes a 422 on the REST call, retry with `body: "Inline comments for AI review"` as a non-empty fallback. Document this fallback in the agent file.

  **Step 6: Log completion.**
  Log: `AI review posted on PR #$PR_NUM ({N} findings, {M} inline comments)`

  **Error handling throughout:**
  - Every `gh` command must have `2>/dev/null || true` or equivalent graceful handling
  - The agent must NEVER cause verify-work to abort
  - If any step fails, log one line and continue to the next step (or exit gracefully if critical data is missing)

  **What NOT to include:**
  - Do NOT approve or request changes on the PR
  - Do NOT close or merge the PR
  - Do NOT modify any local files (this agent is read-only + GitHub posting)
  - Do NOT post more than 5 inline comments
  - Do NOT reference line numbers from deleted lines in the diff

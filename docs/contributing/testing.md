# Testing

VIT has an automated test pipeline that generates tests after each phase executes and runs them on every push to feature branches. This guide explains how the system works, where tests live, and how to write and run tests for new VIT features.

## Overview

The test pipeline has three parts:

1. **`vit-test-writer` agent** — generates Vitest tests from PLAN.md `must_haves` after a phase completes
2. **`tests/phases/`** — where test files live, organized by milestone
3. **`phase-ci.yml`** — GitHub Actions workflow that runs tests on push and posts results to the phase's GitHub issue

## vit-test-writer Agent

`vit-test-writer` is spawned automatically by `/vit:execute-phase` after all waves in a phase complete. It reads what was built and writes tests that verify the plan's promises.

### What it does

For each plan in a phase, `vit-test-writer`:

1. Reads `must_haves` from the PLAN.md frontmatter — the observable truths, required artifacts, and key links the plan promised to deliver
2. Reads SUMMARY.md to understand what actually shipped and which implementation choices were made
3. Writes a Vitest test file covering each testable behavior

### What it tests

The agent tests promises, not implementations:

**It tests:**
- File existence and minimum content (artifact checks)
- Export shapes and function signatures
- Required patterns present in source files (e.g., `gh pr create --draft` is in execute-phase.md)
- API endpoint response shapes (status codes, body structure)
- Auth/scope guards returning 403 when missing

**It does not test:**
- Visual rendering or CSS layout
- Manual user flows
- Database migrations (those belong in integration tests)
- Claude's AI response content

### When it runs

Spawned by `/vit:execute-phase` at step 6.5, after all plan waves complete and before the verifier runs:

```
Task(
  prompt="First, read ./.claude/agents/vit-test-writer.md...\n\nPhase: {phase}\nWorking directory: {work_dir}\nPlans to cover: {plan_list}",
  subagent_type="general-purpose",
  model="{executor_model}",
  description="Write tests for Phase {phase}"
)
```

Test generation is non-blocking — if the agent fails, execution continues.

### Output

Returns `## TESTS WRITTEN` with a coverage table:

```
## TESTS WRITTEN

Plans covered: 3

| File                                        | Tests | Status   |
|---------------------------------------------|-------|----------|
| tests/phases/v1.1.0/02-03-command-anatomy.ts  | 8     | ✓ pass   |
| tests/phases/v1.1.0/02-04-reference-pages.ts  | 5     | ✓ pass   |
```

## Test Location

Tests live in `tests/phases/{milestone}/`:

```
tests/
  phases/
    v1/
      01-01-pr-column-and-draft-pr-creation.test.ts
      01-02-pr-promotion-in-verify-work.test.ts
      02-01-vit-pr-reviewer-agent.test.ts
    v1.1.0/
      02-01-vitepress-foundation.test.ts
      02-03-command-anatomy.test.ts
```

### Naming convention

```
{phase-number}-{plan-number}-{plan-slug}.test.ts
```

Examples:
- `02-03-command-anatomy.test.ts` — Phase 02, Plan 03
- `01-01-pr-column-and-draft-pr-creation.test.ts` — Phase 01, Plan 01

One test file per plan. Tests within it map directly to the plan's `must_haves`.

### Test file structure

```typescript
/**
 * Phase {NN}: {Phase Name} — Plan {plan}: {Plan Name}
 *
 * Tests verify must_haves from {NN}-{plan}-PLAN.md
 * Generated by vit-test-writer after phase execution
 */
import { describe, it, expect, beforeAll } from 'vitest'
import { readFileSync, existsSync } from 'node:fs'
import { join } from 'node:path'

const WORK_DIR = join(import.meta.dirname, '..', '..', '..')

function read(relPath: string): string {
  const abs = join(WORK_DIR, relPath)
  if (!existsSync(abs)) throw new Error(`File not found: ${abs}`)
  return readFileSync(abs, 'utf8')
}

function exists(relPath: string): boolean {
  return existsSync(join(WORK_DIR, relPath))
}

describe('Phase {NN}-{plan}: {Plan Name}', () => {
  // Group tests by must_have truth
  describe('Truth: {observable behavior}', () => {
    it('file exists', () => {
      expect(exists('path/to/file.md')).toBe(true)
    })

    it('contains required pattern', () => {
      const content = read('path/to/file.md')
      expect(content).toContain('required string')
    })
  })
})
```

For projects with TypeScript modules (not just Markdown files), tests import real modules and mock external dependencies:

```typescript
import { vi } from 'vitest'

// Mock database — never mock the module under test
vi.mock('$lib/server/db', () => ({ db: mockDb }))

it('returns 403 when scope is missing', async () => {
  const response = await handler(requestWithoutScope)
  expect(response.status).toBe(403)
})
```

## phase-ci.yml: The CI Workflow

`.github/workflows/phase-ci.yml` runs on every push to `feature/**`, `milestone/**`, and `quick/**` branches.

### What it does

1. **Checks out the repo and installs dependencies** (`npm ci`)
2. **Runs type checking** (`npm run type-check`, non-blocking)
3. **Runs phase tests** — looks for test files in `tests/phases/`, runs them with Vitest
4. **Parses results** — extracts passed/failed counts from the JSON reporter output
5. **Finds the linked GitHub issue** — reads the feature branch name, extracts the milestone and phase number, looks up the issue number in `.planning/STATE.md`
6. **Posts results to the GitHub issue** — a comment with pass/fail count, failing test names, and a link to the Actions run

### Trigger conditions

```yaml
on:
  push:
    branches:
      - 'feature/**'
      - 'milestone/**'
      - 'quick/**'
```

Every push to a feature branch triggers the workflow. This means CI runs after each commit — you get test feedback within minutes of pushing.

### What it posts to GitHub

**All tests pass:**
```
✅ CI Passed — Phase v1.1.0/02 @ abc1234

Branch: feature/v1.1.0-02-03
Tests: 12/12 passed

All unit tests green. Ready for human review.
Run `/vit:verify-work 02` to complete manual UAT.
```

**Tests fail:**
```
❌ CI Failed — Phase v1.1.0/02 @ abc1234

Branch: feature/v1.1.0-02-03
Tests: 10/12 passed — 2 failing

Failing tests:
  FAIL  tests/phases/v1.1.0/02-03-command-anatomy.test.ts
    ✗ contains cross-link to agent-anatomy
```

**No tests yet:**
```
🔄 CI — Phase v1.1.0/02 @ abc1234

Status: No phase tests yet — waiting for test generation
Tests are created by `vit-test-writer` after phase execution completes.
```

### Issue lookup

The workflow extracts the issue number by parsing the branch name:

```bash
BRANCH="feature/v1.1.0-02-03"
MILESTONE=$(echo "$BRANCH" | sed 's|feature/||' | grep -o '^v[0-9]*\.[0-9]*\.[0-9]*')
PHASE=$(echo "$BRANCH" | sed "s|feature/${MILESTONE}-||" | grep -o '^[0-9]*')
ISSUE=$(grep "| ${MILESTONE}/${PHASE} " .planning/STATE.md | grep -o '#[0-9][0-9]*' | head -1 | tr -d '#')
```

This means the branch name and STATE.md mapping must be consistent for CI posting to work. Both are set up automatically when you run `/vit:execute-phase`.

For more details on the full GitHub integration — issue creation, PR promotion, and milestone tracking — see [GitHub Integration](/reference/github-integration).

## Writing Tests for VIT Features

### For Markdown-based features (commands, agents, workflows)

VIT's source files are mostly Markdown. Tests for them check file existence and required content patterns:

```typescript
describe('Truth: Command spawns agent via Task()', () => {
  let content: string

  beforeAll(() => {
    content = read('files/commands/vit/my-command.md')
  })

  it('file exists', () => {
    expect(exists('files/commands/vit/my-command.md')).toBe(true)
  })

  it('contains Task() call', () => {
    expect(content).toContain('Task(')
  })

  it('reads agent file before passing context', () => {
    expect(content).toMatch(/read.*agents\/vit-my-agent\.md/)
  })

  it('resolves model from config before spawning', () => {
    expect(content).toContain('MODEL_PROFILE')
  })
})
```

**What to check for commands:**
- The command exists at the expected path
- Key bash commands or patterns are present
- Flag parsing logic is present
- Model resolution is done before Task() calls
- Structured return headers are present

**What to check for agents:**
- The agent file exists
- The `<role>` section is present
- Required sections exist (`<execution_flow>`, `<success_criteria>`)
- Key domain-specific patterns are present

### For TypeScript features (utilities, API routes)

When a phase adds TypeScript modules, test the public API directly:

```typescript
import { generateApiKey } from '../../src/lib/api-keys'

describe('API key generation', () => {
  it('prefixes with sk_live_ for production keys', () => {
    const key = generateApiKey('live')
    expect(key).toMatch(/^sk_live_[a-z0-9]+$/)
  })

  it('prefixes with sk_test_ for test keys', () => {
    const key = generateApiKey('test')
    expect(key).toMatch(/^sk_test_[a-z0-9]+$/)
  })
})
```

**Mocking strategy:**
- Mock external dependencies (database, HTTP clients) using `vi.mock()`
- Never mock the module you're testing
- Test the public exported functions, not internal implementation details

### What NOT to test

Some things belong in manual UAT (run via `/vit:verify-work`), not automated tests:

- Visual appearance and layout
- Interactive user flows (click through a wizard)
- Real-time behavior (WebSocket updates)
- External service integrations (actual Stripe charges, real email sends)
- Performance and feel

The `vit-verifier` agent handles structural verification of these. Human UAT handles the rest.

## Running Tests Locally

```bash
# Run all phase tests
npx vitest run tests/phases/

# Run tests for a specific milestone
npx vitest run tests/phases/v1.1.0/

# Run tests for a specific plan
npx vitest run tests/phases/v1.1.0/02-03-command-anatomy.test.ts

# Watch mode during development
npx vitest tests/phases/
```

If you're adding tests manually (not generated by `vit-test-writer`), run them locally before pushing to confirm they pass.

### Vitest config

Phase tests use the project's existing `vitest.config.ts` or `vite.config.ts`. The test runner looks for files matching `tests/phases/**/*.test.ts`. If your project's vitest config doesn't include this glob, add it:

```typescript
// vitest.config.ts
export default defineConfig({
  test: {
    include: ['tests/**/*.test.ts', 'src/**/*.test.ts'],
  },
})
```

## Summary

| What | Where |
|------|-------|
| Test files | `tests/phases/{milestone}/{NN}-{plan}-{slug}.test.ts` |
| Generated by | `vit-test-writer` (spawned by `/vit:execute-phase`) |
| CI workflow | `.github/workflows/phase-ci.yml` |
| CI triggers | Push to `feature/**`, `milestone/**`, `quick/**` |
| CI posts to | GitHub issue linked to the phase |
| Run locally | `npx vitest run tests/phases/` |
